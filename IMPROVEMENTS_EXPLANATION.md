# Mini Python compiler: implementation and demonstration guide

## Project objective

This version accepts Python source in a documented subset, translates it through compiler stages, optionally optimizes the intermediate representation, and executes generated bytecode in the custom stack VM:

```text
Python source -> Python AST -> three-address IR -> optional optimizer -> bytecode -> CVM
```

It is not a compiler for arbitrary Python. Full Python includes dynamic objects, classes, imports, exceptions, closures, generators, and runtime protocols that need a much larger compiler and runtime. Unsupported syntax is rejected with a source line number rather than being silently miscompiled.

## Implemented language and features

### Python frontend (`python_frontend.py`)

Supported source constructs:

- Integer literals and local variables.
- Boolean literals lowered to integer truth values (`False` → `0`, `True` → `1`).
- Fixed-size integer tuple literals assigned to local names and accessed using constant in-range indexes, including negative indexes.
- `+`, `-`, `*`, Python `//` and `%`, and one comparison per condition/expression.
- Assignment and augmented assignment such as `total += value`.
- `if`/`else`, `while`, and `for` over `range` with a literal nonzero step.
- Direct functions, positional arguments, recursion, and `return`.
- `print` of integer expressions, top-level script statements, or a `main()` function guarded by the common `if __name__ == "__main__": main()` pattern.
- Fifteen `parallel_*` integer reductions described below.

Not supported: floats, strings as values, lists, dictionaries, dynamic tuple indexing, mutable containers, tuple creation/copying inside branches or loops, classes, imports, exceptions, closures, decorators, keyword/default arguments, `break`, `continue`, chained comparisons, and arbitrary Python library code. Python `//` and `%` use Python's floor and modulo rules, including for negative values. Existing text IR `/` and `%` keep their previous truncation-toward-zero rules.

### IR optimizer (`optimizer.py`)

The optimizer builds basic blocks from function IR and solves forward constant-propagation dataflow to a fixed point. At a branch join, it retains a constant only when all incoming paths agree. Loop back-edges participate, allowing loop-invariant values to propagate while changing values remain unknown. It also solves backward CFG liveness (`IN = USE ∪ (OUT − DEF)`, `OUT = union(IN(successors))`) and uses those sets to remove dead pure stores. Local copy propagation, constant folding, and algebraic simplifications run before liveness cleanup. Division and modulo operations that could trap are retained when they cannot safely be folded. Copy propagation invalidates aliases on reassignment so a saved value remains a snapshot of its original value.

### Runtime parallelism (`PAR_SUM` and `PAR_REDUCE` bytecode instructions)

Every reduction runs a compiled worker for each integer in `range(start, stop)` using a process pool. Inputs are grouped into batches to reduce dispatch overhead; each input still gets a fresh VM and isolated frame. The supported calls are:

| Intrinsic | Result |
|---|---|
| `parallel_sum` | Sum of worker results |
| `parallel_product` | Product of worker results |
| `parallel_min`, `parallel_max` | Smallest or largest worker result |
| `parallel_count` | Number of nonzero worker results |
| `parallel_any`, `parallel_all` | Integer truth result (`0` or `1`) |
| `parallel_bit_and`, `parallel_bit_or`, `parallel_bit_xor` | Bitwise combination of integer results |
| `parallel_gcd`, `parallel_lcm` | Greatest common divisor or least common multiple |
| `parallel_average` | Floor of sum divided by result count; remains an integer |
| `parallel_argmin`, `parallel_argmax` | Input whose worker result is the minimum or maximum |

For equal extrema, argmin/argmax choose the lowest input. Empty-range identities are: sum/count/any/bitwise OR/bitwise XOR/GCD = `0`; product/all/LCM = `1`; bitwise AND = `-1`. Min/max/average/argmin/argmax raise a runtime error because an empty range has no defined result for those operations.

For safety and deterministic reduction, a worker must accept exactly one argument and may contain local integer arithmetic and control flow only. Worker functions cannot print, call another function, or invoke nested parallel reductions. The range is capped at 100,000 inputs. The result of the parallel sum example is compared with a separate sequential program that performs the same calculation.

There are two distinct parallel features:

- `parallel_*` reductions perform actual process-level parallel program work.
- `--parallel-opt` (also available as the older alias `--parallel`) optimizes independent functions concurrently in the compiler.

## Dataflow, bytecode, and expanded demonstrations

The optimizer's public `analyze_liveness(function)` helper returns each basic block's live-in and live-out variable sets. The optimizer uses the same analysis to remove dead pure assignments safely across control-flow edges; operations that may divide by zero stay in the program even when their result is unused.

`isa.encode` now emits a versioned bytecode header (`CVM`, version byte, instruction count). `isa.decode` rejects unknown versions and continues to read the earlier `CVM1` layout. The instruction encoding remains fixed-width, so version changes can be checked before any instructions are executed.

The bounded type demonstration is `examples/python_types.py`; it illustrates boolean truth values and fixed tuples with static indexing. `examples/python_parallel_reductions.py` runs all fifteen reductions. `performance_study.py` runs multiple sequential and process-parallel measurements at configurable input sizes, verifies equal outputs, and reports the timing median/range and VM work. Timing includes process startup and is not a portable speed guarantee.

Process startup and serialization are expensive, so small parallel ranges can be slower than sequential execution. The project demonstrates real concurrent process execution and result equivalence; it does not claim speedup for every workload.

## Commands for a demonstration

Run the Python frontend examples:

```sh
python3 main.py examples/python_sum.py --opt --stats
python3 main.py examples/python_factorial.py --stats
```

Compare the exact same optimization example before and after optimization in one checked run:

```sh
python3 main.py examples/python_optimization_workload.py --compare
```

Both versions print `17220`. The baseline executes 693 VM instructions and emits 60 static bytecode instructions; the optimized version executes 477 and emits 34. That is a **31.2% reduction in executed instructions** and a **43.3% reduction in static bytecode** for this workload. The optimizer folds the loop-invariant multiplier, removes the `+ 0`, and deletes unused computations. `--compare` checks that outputs match. This is an instruction-count comparison, not a wall-clock benchmark.

For repeated local timing, run `python3 main.py examples/python_optimization_workload.py --benchmark 5`. This executes both versions five times and reports minimum, median, and mean wall time alongside instruction counts. Timings include VM setup and are machine- and load-dependent, not a portable speed guarantee. On `examples/sum.ir`, CFG propagation preserves output `55`, reduces static bytecode from 28 to 26 instructions, and reduces executed instructions from 169 to 167.

Show equivalent sequential and process-parallel computation:

```sh
python3 main.py examples/python_sequential_sum.py --stats
python3 main.py examples/python_parallel_sum.py --stats
```

Both produce `332833500`, the sum of squares from 0 through 999. The unoptimized sequential VM executed 19,019 instructions. The parallel VM reports 1,000 independent inputs dispatched across up to the host's available worker-process count (8 in the measured run). It executes 13 instructions in the parent VM and 10,000 across the worker VMs, for 10,013 counted VM instructions total compared with the sequential run's 19,019. This is about **47.4% fewer VM instructions** for this example, but it does not include process startup and serialization costs. It proves worker execution and equivalent output, not lower wall-clock time. Use repeated `--benchmark` runs to measure elapsed time on the presentation machine.

Inspect the generated IR and bytecode:

```sh
python3 main.py examples/python_parallel_sum.py --ir --dis --no-run
python3 main.py examples/python_sum.py --cfg
python3 main.py examples/python_types.py --opt --stats
python3 main.py examples/python_parallel_reductions.py --stats
python3 performance_study.py --sizes 1000 5000 --runs 5
```

Run the tests:

```sh
python3 tests.py
```

## How to explain the architecture

1. Python's `ast` module parses the `.py` file into syntax nodes.
2. `python_frontend.py` walks those nodes and emits the same three-address IR used by `.ir` inputs. For example, a Python `for` loop becomes initialization, a comparison, a conditional jump, a body, an increment, and a backward jump.
3. With `--opt`, the IR optimizer folds values and removes redundant computations before code generation.
4. `codegen.py` assigns local slots, emits stack bytecode, and patches function and branch addresses.
5. The VM executes the bytecode. `PAR_SUM` and `PAR_REDUCE` dispatch isolated worker VMs in child processes; the parent applies the selected integer reduction to the returned values.
6. `--stats` shows IR size, emitted bytecode size, parent-VM instruction count, worker-VM instruction count, and the parallel task/worker count when the program uses a parallel reduction.

## Likely viva questions

**Q: Does this compile all of Python?**  
A: No. It compiles a documented integer-oriented subset and reports unsupported constructs. Full Python would require dynamic object semantics, a much larger runtime, and extensive additional compiler work.

**Q: What is the difference between compiler parallelism and runtime parallelism here?**  
A: `--parallel-opt` runs independent IR optimization jobs concurrently during compilation. `parallel_sum` executes the compiled worker function concurrently in separate processes at runtime.

**Q: Why use processes for `parallel_sum`?**  
A: Processes can execute Python VM work on multiple CPU cores without relying on Python threads for CPU parallelism. Each process runs a separate VM with its own stack and frame.

**Q: How do you know the parallel result is correct?**  
A: The project includes a sequential reference program and a parallel program that compute the same sum of squares. They both print `332833500`; an automated test checks the parallel result.

**Q: How do you compare the parallel and sequential instruction counts fairly?**  
A: Add the parent VM count to the sum of the worker VM counts. That gives 10,013 versus 19,019 on the included workload. Use `--benchmark N` for repeated wall-clock measurements; these include process startup and dispatch and can show a different result from instruction counts.

**Q: Why restrict the parallel worker?**  
A: Independent tasks must not have shared side effects if we want a deterministic reduction. The current worker contract allows local integer computation and control flow, and rejects printing, calls, and nested parallelism.

**Q: What is the optimizer's measured effect?**  
A: On the included 20-iteration scoring workload, output stays `17220` while static bytecode falls from 60 to 34 and executed VM instructions from 693 to 477. A smaller example isolates constant folding; the loop and CFG examples show behavior on longer control flow. Improvements depend on the workload.

**Q: How does the optimizer handle loops and branches?**  
A: It iterates constant facts over basic-block predecessor edges until they stabilize. A join keeps only facts shared by every predecessor, including loop back-edges. A changing induction variable is not treated as constant.

**Q: What does liveness add?**  
A: Liveness walks the CFG backward to find which variables can still be read. It lets the optimizer remove a pure assignment when its result cannot reach a later use, even when the use is in another block. Potentially trapping division/modulo operations remain to preserve runtime errors.

**Q: Does the compiler now support Python containers?**  
A: It supports a narrow fixed-tuple feature: a non-empty integer tuple assigned to a local name and accessed with a compile-time constant index. This lowers each tuple element to a scalar local; dynamic indexing, lists, and mutation are still outside the supported subset.

**Q: What parallel operations are implemented?**  
A: Sum, product, min, max, nonzero count, any, all, bitwise AND/OR/XOR, GCD, LCM, integer floor average, argmin, and argmax. Argmin/argmax return the input associated with the extreme worker result; ties choose the lowest input.

**Q: What happens on an empty input range?**  
A: Reductions with a defined identity return it: sum/count/any/OR/XOR/GCD return zero, product/all/LCM return one, and bitwise AND returns minus one. Min/max/average/argmin/argmax report a runtime error.

**Q: How does the bytecode version work?**  
A: Newly emitted files carry a version byte that the decoder checks before reading instructions. The decoder also retains compatibility with the previous `CVM1` file layout; unknown future versions fail with a clear error.

**Q: How do you measure runtime?**  
A: `--benchmark N` runs baseline and optimized programs N times, checks their outputs, and reports min/median/mean wall time plus VM instruction counts. For `parallel_sum`, process setup and scheduling are included, so small workloads can be slower.

## Limitations and next extensions

- The supported Python syntax is intentionally small. The only container feature is fixed tuples with constant indexing; lists, dictionaries, mutable containers, type inference, globals, exceptions, and standard library integration are absent.
- The optimizer has CFG constant propagation and backward liveness, but it does not implement SSA or a broad suite of dataflow optimizations such as reaching definitions.
- Runtime reductions support fifteen integer operations over a pure one-argument worker; they do not implement general Python multiprocessing semantics. `parallel_average` is floor division, count means nonzero results, and argmin/argmax return input values.
- Parent VM step counts and summed worker VM steps are reported separately. `--benchmark` measures wall time including process startup, serialization, and scheduling; results remain machine- and load-dependent.
- The CFG drives optimizer analysis, while bytecode generation still consumes the transformed linear function IR.
- The binary format remains fixed-width instruction based. New files are versioned and this decoder reads the previous `CVM1` layout, but older VM builds cannot execute newer reduction opcodes.
